# 공온 제품 요약 (현재 요구사항, 2026-10-16)

이 문서는 **지금 무엇을 누구를 위해 만드는지**만 짧게 적는다. 세부 규칙은 결정(`decisions.md`)·계약(`collab-contract.md`, 기상 판정은 `contract.md`)·작업 순서(`plan.md`)가 기준이고, 여기서는 그 번호를 연결한다. 기획이 바뀌면 결정을 남기고 **이 문서도 같은 작업에서 고친다**(D-068). 2026-10-16 이전의 긴 기획 문서(서비스_개발_총정리, 개발기획서 v2.1)는 삭제했으며 Git 이력에만 있다.

## 1. 무엇을 만드는가

**공사 계획이 바뀔 때 함께 바꿔야 할 일을 관련 업체·담당자에게 연결하고, 실제 처리 근거와 검증까지 남기는 서비스**다(D-055).

- 중심 흐름: `예정 작업 → 변경 건 → 확정 버전 → 업체별 후속 조치 → 완료 보고·근거 → 검증`.
- 계획을 고쳤거나 메시지를 읽었다는 사실만으로 실제 예약·출역 변경이 끝났다고 처리하지 않는다.
- 변경 원인은 공정·선행 작업, 인력, 장비, 자재, 도면·설계, 품질·검측, 안전·작업 허가, 구역·동선, 비용·계약, 외부 조건, 기상(복수 선택). **날씨는 그중 하나다**(D-065).
- **변경과 이어진 서류를 공온 기록으로 만들어 준다**(D-112): 주간 작업계획표(공정회의 자료), 작업일보·공사일보, 기상 작업중지 기록, 변경 건 문서(작업 지시서·실정보고 초안). 인쇄·PDF 저장용이며 공식 서류를 대신하지 않는다. 작업 차질 월 집계(원인별 일부만·못함, 언제 알았나, D-113)도 둔다. 작업일보는 조정자 또는 그 작업을 맡은 업체 담당자가 오늘까지의 작업에 남긴다. 서류는 주 메뉴 ‘서류’ 탭에 모으고(D-116), 작업 지시서·실정보고 초안은 변경 건 상세에서 연다. 검측·자재 승인·품질시험·사진첩·안전서류 일반·기성은 하지 않는다.
- 비상업 시연 범위(D-014)다. 실제 고객·내부 자료 없이 공개 자료와 `[가상]` 합성 사례로 구현하고(D-056), 현장 효과는 C08에서 따로 검증한다.

## 2. 누가 쓰는가 (D-066·D-067)

| 사용자 | 하는 일 | 화면 |
| --- | --- | --- |
| **원청 현장 공사·공무 담당자(주 사용자)** | 작업 등록, 변경 제안·확정, 조치 배정, 업체·담당자 명부 관리 | 전체(조정자) |
| 원청 안전·품질 담당 | 완료 보고 검증 | 담당자 |
| 소장 | 현황 보기 | 조정자·열람자 |
| 협력업체 현장대리인·반장 | 맡은 조치 응답·막힘·완료 보고(휴대폰) | 담당자 |
| 감리·CM | 보기(연락처 제외) | 열람자 |
| 작업자·기사 | 오늘·내일 작업 보기 | 현장 게시 화면(C11, 가입 불필요) |

- 프로젝트 = 현장(Site). 같은 회사여도 현장 참여 없이는 볼 수 없다. 조정자는 원청 소속만(D-057).
- 현장을 만든 사람이 조정자다. 다른 사람은 조정자가 번호로 추가하거나, 조정자에게 받은 현장 코드(8자리)로 스스로 담당자로 들어온다(D-095).
- 모든 작업자의 가입을 도입 조건으로 두지 않는다. 계정 없는 담당자의 응답은 조정자의 전화 확인 기록으로 남긴다.

## 3. 반드시 지킬 동작

1. 기존 작업을 골라 변경 전후·원인·근거를 등록하고, 사람이 영향과 누락을 검토한 뒤 확정한다. 제안자·확정자·수행자·검증자를 구분한다(D-060).
2. 확정할 때 계획 버전·후속 조치·발송 대기를 한 트랜잭션으로 저장한다. 조치마다 대상 버전·수행자·검증자·필수 여부·기한(없으면 미정 사유)을 둔다(계약 §5).
3. 전송·열람·응답·완료 보고·검증 완료를 따로 기록하고, 막힘·반려·제외·위임의 이유와 행위자를 남긴다.
4. 현재 확정 버전의 필수 조치가 모두 검증·제외되고 막힘이 없을 때만 변경 건을 닫는다. 조치가 모두 끝나면 저절로 닫히고, 수락·기한 사유·보류 담당·처리 시각처럼 형식만 늘리는 입력은 선택이거나 기본값이다(D-114). 필수 0건이면 이유가 필요하다. 필수 조치를 지워 우회하지 않는다.
5. 재변경은 새 버전이다. 이전 기록은 보존하고 새 버전의 완료로 자동 승계하지 않는다. 이미 끝난 외부 예약은 DB 취소로 원복되지 않으므로 보완 조치를 사람이 지정한다(C07).
6. 전화로 확인한 대리 기록과 직접 응답을 구분한다(연락 상대·회사·시각·기록자).
7. 조치 검증은 등록된 근거의 확인이다. 공식 검측·작업 허가·계약 변경 승인·현장 안전 적합성을 대신하지 않는다. 긴급 대응을 공온 입력이 끝날 때까지 기다리게 하지 않는다.

## 4. 공온 점검과 기상 판정

- **작업 고르기**(D-085): 작업은 업종 → 업무분야 → 작업으로 고른다(업종은 건설산업기본법 시행령 별표 1). 날씨 판정은 작업이 판정 공종일 때만 하고, 나머지 작업은 폭염만 판정한다.
- **공온 점검**(D-065): 작업마다 날씨(내일 작업)·실행 업체 미지정·작업 위치 없음·같은 곳 같은 시간 겹침·확정 전 변경을 확인한다. 등록 자료로 하는 규칙 점검이며 새 기준 수치를 만들지 않는다.
- **기상 판정**은 근거 모듈로 유지한다: `진행 / 확인 필요 / 중지 검토 / 판정 불가` 이름과 저장 계약(`contract.md`·`schema.json`)을 바꾸지 않는다. 규칙 기반·LLM 없음, 같은 입력·같은 기준 버전 → 같은 결과. 근거가 없거나 예보로 직접 비교할 수 없으면 ‘중지 검토’로 올리지 않는다. 누락을 정상값으로 채우지 않는다. 원문 대조 전 기준은 `[원문 대조 필요]`.
- 판정 범위는 내일부터 7일(D-041), 오늘 작업은 판정하지 않는다(D-061). 공온지수 v2(D-052, 중기 참고 날은 D-069)는 제품 설계값이며 확률·안전 보장이 아니다.
- 예보·현장 관측·담당자 결정·후속 조치·실제 작업 결과는 구분해 저장한다. 예보로 실제 중단·예약 취소·일정 확정을 자동 생성하지 않는다. 판정·점검은 작업 허가가 아니며 최종 판단은 현장 책임자가 한다.

## 5. 화면 (D-063~D-065)

- 주 메뉴: 홈 · 일정(달력·공온 판정·판정 내역) · 변경·조치(변경 건·내 조치) · 서류(공사일보·주간 작업계획표·차질 집계, D-116) · 업체 · 대화(D-090). 휴대폰은 아래 탭 막대. 현장 고르기는 머리줄 칩 하나(대화 빼고, 전체 포함)이고 고른 값은 탭을 옮겨도 유지된다. 처음엔 전체(D-091·D-092). 업체는 엑셀 같은 표. 이름 메뉴: 내 정보 · 공온 가이드 · 로그아웃.
- 홈: 오늘(시간표·먼저 챙길 것) → 내일(브리핑) → 이번 주 공온지수.
- 화면에는 설명 문장을 두지 않고 공온 가이드(/guide)에 모은다. 문구는 짧고 가볍게(brand.md ‘공온 말투’).
- 현장·작업 상세의 보조 동작은 `···` 메뉴로 모은다(D-083). 특정 현장의 메뉴는 일정 하위 메뉴 줄 오른쪽 끝에 두며 전체 현장은 숨긴다. 현장 수정·삭제와 작업의 변경 제안·삭제는 모달로 열고, 홈의 빈 일정 안내는 해당 현장·날짜의 작업 추가로 연결한다.
- 웹 입구(D-110, 슬랙 방식): `/`는 서비스 사이트다. 로그인 전에는 첫 화면과 그 아래 공온 이야기(D-115), 로그인 뒤에는 내 현장 고르기에서 현장을 눌러 PC 웹 앱(`/home`)으로 들어간다. 머리줄은 메인·제품(기능 페이지)·협업·요금이고 각각 각자 페이지이고 드롭다운 없이 바로 간다(소개 메뉴는 없음, D-115). 바닥글은 서비스 사이트에만. 휴대폰 앱 화면은 서비스 사이트 없이 바로 앱 홈.
- 휴대폰은 PC 화면을 줄인 것이 아니라 따로 설계한 앱 화면이다(D-109, 슬랙 방식). 기능은 거의 같고 배치만 다르다: 휴대폰 첫 화면은 내 할 일, PC는 현황판. PC에서만 업체 표 편집·작업 일괄 등록·관리. 서버·DB는 하나이고 앱은 휴대폰 화면을 감싼 껍데기(안드로이드 APK 먼저, 아이폰은 당분간 웹)다.
- 기본 알림은 웹·미리보기다. 실제 카카오톡 알림톡은 사업자 등록 뒤(D-015). 미리보기를 ‘발송됨’으로 표시하지 않는다.

## 6. 범위 밖 (지금 만들지 않는 것)

자동 발주·예약 취소, 인력 매칭·결제, 회사 전체 채널·1:1 개인 대화 같은 범용 메신저, 공사비 자동 승인, 전체 공정 최적화, 제품 안의 LLM 호출, 권한 없는 공개 링크·QR(D-067), PMIS 전체 대체·전체 연동. 변경 건·조치에 붙는 대화 기록은 C06·C07에, **현장 단위 대화방**(그 현장 참여자만, 메시지에서 변경 제안·조치 만들기)은 C12에 들어간다(D-071). 다음 확장 후보는 도면·근거 변경의 재검토 요청(C09), 현장 간 자원 배치 협의(C10)이며 반복 사용·별도 수요가 확인된 뒤 시작한다.

## 7. 실제 시험·서비스화 전에 확인할 것

| 항목 | 확인 내용 |
| --- | --- |
| 도입 | 현장 후원자·본사 도입·보안·구매 절차, 시험 허용 범위 |
| 권한 | 변경 전결·업체 수행·검증·위임·긴급 보고 경로, 수행자=검증자 허용 여부(지금은 금지) |
| 정보 | 업체·첨부 접근, 민감 자료·연락처 보관 기간·동의, 퇴사자 처리 |
| 외부 조치 | 예약·출역의 실제 처리 주체와 확인 근거, 공급사 참여 방식 |
| 기상 모듈 | 원문 대조·단위·시각·판단 보조 문구, 데이터 이용 조건 |
| 상업 운영 | 등록 필요 여부·약관·비용·계정·실발송 조건(D-014·D-015 유지) |
| 효과 | 총 업무(입력·전화·재확인·교육 포함)·처리/검증 지연·구버전 실행·반복 사용(C08). 임의 절감률·시장 규모를 쓰지 않는다 |

이 표는 확인 항목이며 법률 판단이 아니다. 실제 조건 확인 전 법적 승인·손실액을 확정하는 기능을 만들지 않는다.

## 8. 기술 구성

Python · FastAPI · PostgreSQL · 서버 렌더링(Jinja) · 휴대폰 앱은 같은 화면을 띄우는 웹뷰 껍데기(D-109) · 규칙 기반 판정(YAML 기준표) · pytest + GitHub Actions. 개발은 Claude Code와 Codex가 같은 저장소 규칙(`AGENTS.md`)으로 이어받는다. 실행 명령은 `setup.md`, 구조는 `architecture.md`.
