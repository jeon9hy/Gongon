## 2. 공정표의 구조: 묶음과 작업

CSV 한 줄이 공온의 **작업 한 건**이다. 단위는 `동·층·구역 × 작업 종류 × 날짜`다.

| 열 | 뜻 | 지금 공온에 있나 |
| --- | --- | --- |
| 작업ID | `101-9F-벽체철근`, `102-8F-Z3-타설`처럼 읽을 수 있는 키 | 없음(숫자 ID) |
| 날짜·시작·종료 | 작업 시각(KST) | 있음 |
| 동·층·구역 | 위치. 층과 구역은 진행 단위 | 위치 문자열 하나 |
| 묶음 | `101동 9층 골조`처럼 한 층 사이클 | 없음 |
| 작업 | 실제 하는 일(벽체 철근, 슬라브 형틀…) | 없음. 공종 목록에서만 고름 |
| 업체공종·실행업체 | 책임 단위 | 실행업체 있음 |
| 인원·장비·양중 | 출역 인원, 펌프카·크레인·T/C | 메모로만 |
| 선행작업 | 끝나야 시작할 수 있는 작업ID(여러 개는 `;`) | 없음 |
| 외부 예약·요청 | 레미콘·펌프카·검측 요청 | 없음(변경 시 조치로만) |
| 공온 판정 공종 | 기상 판정을 적용할 공종(`rules/*.yaml`의 이름) | 공종 = 이 값 |

**진행도는 사람이 입력하지 않는다.** 묶음의 진행도는 그 안의 작업이 몇 건 끝났는지로 계산한다. 예: `101동 9층 골조` 18건 중 11건 완료. 각 작업은 `진행 전 → 진행 중 → 종료` 상태를 가진다.

**판정은 작업 단위다.** "철근 공종이라 판정"하지 않는다. 그날 작업이 타설이면 비·기온 기준을, 크레인 양중이면 바람 기준을 적용한다. 90건 중 판정 대상은 22건이다(타설 14, 커뮤니티센터 철골 5, 주차장 방수 3).

## 4. 층 전체 방식과 구역 분할 방식의 차이

| 항목 | 101동(층 전체 9일) | 102동(4구역 4일) |
| --- | --- | --- |
| 2주 동안 타설 | 2회(약 200㎥씩) | 12회(약 50㎥씩), 작업일마다 |
| 2주 동안 검측 | 2회 | 11회(타설 전날 16시) |
| 작업 행 수 | 23건 | 59건 |
| 하루 밀릴 때 영향 | 그 층 뒤 작업 전부와 다음 층 | 그 구역 뒤 작업과 다음 층 같은 구역. 다른 구역은 계속 진행 |
| 외부 예약 | 레미콘·펌프카를 9일에 한 번 | **매일** 레미콘·펌프카·검측 |

구역을 나누면 공기는 줄지만 **매일 외부 예약과 검측이 생긴다.** 변경 하나가 퍼지는 범위는 좁아지는 대신 변경 횟수가 늘어난다. 공온의 후속 조치 연결이 더 필요한 쪽은 구역 분할 현장이다.

질문에 대한 답: 구역 1·2·3·4는 **진행도를 쪼개는 칸이 아니라 각각 별도 작업**이다. 구역마다 날짜와 선행 조건, 타설 여부가 다르기 때문이다.

| 묶음(층 사이클) | 없음 | 진행도를 보여 줄 수 없다 |
| 선행작업 | 없음 | 하나가 밀릴 때 뒤 작업과 업체를 찾을 수 없다 |
| 구역 | 위치 문자열 | 같은 층의 다른 구역과 연결되지 않는다 |
| 외부 예약·요청 | 변경 확정 때 조치로만 만듦 | 타설마다 반복되는 예약을 미리 알 수 없다 |
| 인원·장비 | 메모 | 같은 펌프카·타설반이 겹치는 것을 점검할 수 없다 |

여기서 바로 나오는 다음 후보(결정 전, 구현하지 않음):

1. 작업 종류와 판정 공종을 분리한다. 작업 종류는 자유롭게 등록하고, 판정 공종은 선택값(없으면 판정하지 않음)으로 둔다.
2. 묶음과 선행작업을 둔다. 진행도는 계산값이다.
3. 작업 종류별 후속 조치 템플릿: 타설이면 위 §6의 조치 목록.
4. CSV 붙여넣기 등록: 이 파일의 열 구성을 입력 형식 초안으로 쓴다.
