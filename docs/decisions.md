# 결정 기록

확정한 결정은 다시 논의하지 않는다. 바꿀 때는 새 항목을 추가하고 이전 항목에 `대체됨: D-xxx`를 적는다.

## D-001 저장소 위치 (S00, 2026-10-04)
- 결정: 요구사항 MD가 있던 `%USERPROFILE%\OneDrive\바탕 화면\새 폴더`를 저장소 루트로 사용. 기존 MD는 위치·내용을 바꾸지 않는다(커밋 범위는 D-009).
- 이유: 기존 코드가 없고, 작업 폴더로 열려 있던 위치다. 두 도구가 같은 경로를 연다.
- 영향·주의: OneDrive 동기화 폴더라 `.venv`·`.git`이 동기화되고 파일 잠금이 생길 수 있다. 문제가 생기면 동기화되지 않는 경로(예: `C:\dev\...`)로 폴더째 옮기고 `docs/handoff.md`의 저장소 경로를 갱신한다(이동은 개발자가 결정).

## D-002 실행 환경: Python 3.12 + uv (S00)
- 결정: Python 3.12(`.python-version`), 의존성 관리 uv, 잠금 파일 `uv.lock`. `[tool.uv] package = false`로 저장소 루트에서 `engine`·`app`을 import한다.
- 이유: 잠금 파일 하나로 두 도구·CI가 같은 버전을 쓴다. 단일 앱이라 배포 패키지 빌드가 필요 없다.

## D-003 검증 도구 (S00)
- 결정: ruff(린트+포맷, `DTZ` 규칙 포함), mypy `strict`(루트 전체), pytest, GitHub Actions(`.github/workflows/ci.yml`). 명령은 `docs/setup.md`.
- 이유: 시간대 없는 datetime을 정적 검사로 막고, 타입을 계약의 일부로 다룬다.

## D-004 화면 기술: FastAPI + Jinja2 서버 렌더링 (S00 결정, S05에서 의존성 추가)
- 결정: 기능별 `templates/`에 Jinja2 템플릿. 별도 프런트엔드 프레임워크·JS 빌드 없음.
- 이유: 첫 화면은 현장 설정·근거 상세·기록 조회 수준이다. 단일 앱·1인 개발에서 배포 단위와 의존성을 늘리지 않는다.
- 재검토 조건: 상호작용이 많은 일정 화면(S08 이후)에서 서버 렌더링으로 부족함이 확인될 때.

## D-005 DB 접근: SQLAlchemy 2 + Alembic + psycopg 3 (S00 결정, S04에서 의존성 추가)
- 결정: PostgreSQL(Supabase). 마이그레이션은 Alembic, 위치 `migrations/`.
- 미정: 로컬 테스트용 PostgreSQL 준비 방법(Docker 미설치 확인, 2026-10-04). S04 시작 시 로컬 설치 / Docker / 별도 Supabase 개발 프로젝트 중 선택해 기록한다.

## D-006 기능 경계를 테스트로 강제 (S00)
- 결정: `tests/test_import_boundaries.py`가 `engine ↛ app`, `engine.judgment ↛ DB·HTTP·웹·forecast·geo` 를 AST로 검사한다. 상대 import 우회도 잡는다.
- 이유: 순수 판정의 재현성(같은 입력 → 같은 결과)과 폴더 경계를 리뷰에만 의존하지 않기 위해.

## D-007 TestClient용 HTTP 의존성은 httpx2 (S00)
- 결정: 개발 의존성에 `httpx2`. 설치된 Starlette 1.7이 `httpx` 기반 TestClient를 사용 중단 경고로 표시했다.
- 미정: S02 예보 수집에 쓸 HTTP 클라이언트는 S02에서 결정한다.

## D-008 시각·단위 표기 원칙 (S00, 세부는 S01 계약에서 확정)
- 결정: 모든 시각은 시간대 포함(KST `+09:00`), 이름에 단위·시각 의미를 표기. 계약의 필드 이름·값 형식은 S01 `docs/schema.json`에서 확정한다.
- 참고: Windows에는 IANA 시간대 DB가 없어 `ZoneInfo("Asia/Seoul")`에 `tzdata` 패키지가 필요하다. 한국은 일광절약시간이 없으므로 고정 오프셋 사용도 가능 — S01에서 택일.

## D-009 요구사항 기준 문서는 `서비스_개발_총정리.md` 하나 (S00, 2026-10-04, 개발자 지시)
- 결정: 모든 요구사항·기준·운영 방식은 총정리만 따른다. 총정리 머리말에 남아 있는 v2 기획서 참조는 따르지 않는다.
- 처리: 이전 기획서(`공종별_작업가능판단_개발기획서.md`, `_v2.md`)는 개발자 지시로 삭제했다(커밋된 적 없음). 총정리 파일 내용은 수정하지 않는다.
- 영향: 총정리에 없는 기준 세부(예보 항목 형식, 경계 처리 등)는 지어내지 않고 해당 작업에서 원문·공식 문서를 확인해 기록한다.

## D-010 서비스 이름 공온, 브랜드 용어 규칙 (2026-10-04, 개발자 결정)
- 결정: 서비스 이름 **공온**, 코드 식별자 `gongon`. 화면·알림 문구와 용어는 `docs/brand.md`를 따른다.
- 판정 4단계(`진행/확인 필요/중지 검토/판정 불가`)는 브랜드 용어로 바꾸지 않는다. "공사 ON"은 질문형 제목(`내일 공사 ON?`)과 슬로건에만 쓴다 — `진행`도 안전을 보장하지 않는다는 원칙(총정리 §1)과 충돌하지 않게 하기 위해.
- 보류: `공온지수`(점수형 지표)는 총정리에 없는 기능이다. 개발자가 범위에 넣기로 하고 `docs/brand.md` §4 조건을 만족하는 정의를 기록하기 전에는 구현·표시하지 않는다.
- 미확인: 상표·도메인 사용 가능 여부.
