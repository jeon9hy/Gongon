확정한 결정은 다시 논의하지 않는다. 바꿀 때는 새 항목을 추가하고 이전 항목에 `대체됨: D-xxx`를 적는다.

## D-001 저장소 위치 (S00, 2026-10-04)
- 결정: 요구사항 MD가 있던 `%USERPROFILE%\OneDrive\바탕 화면\새 폴더`를 저장소 루트로 사용. 기존 MD는 위치·내용을 바꾸지 않는다(커밋 범위는 D-009).
- 이유: 기존 코드가 없고, 작업 폴더로 열려 있던 위치다. 두 도구가 같은 경로를 연다.
- 영향·주의: OneDrive 동기화 폴더라 `.venv`·`.git`이 동기화되고 파일 잠금이 생길 수 있다. 문제가 생기면 동기화되지 않는 경로(예: `C:\dev\...`)로 폴더째 옮기고 `docs/handoff.md`의 저장소 경로를 갱신한다(이동은 개발자가 결정).

## D-002 실행 환경: Python 3.12 + uv (S00)
- 결정: Python 3.12(`.python-version`), 의존성 관리 uv, 잠금 파일 `uv.lock`. `[tool.uv] package = false`로 저장소 루트에서 `engine`·`app`을 import한다.
- 이유: 잠금 파일 하나로 두 도구·CI가 같은 버전을 쓴다. 단일 앱이라 배포 패키지 빌드가 필요 없다.

- 이유: 시간대 없는 datetime을 정적 검사로 막고, 타입을 계약의 일부로 다룬다.

## D-004 화면 기술: FastAPI + Jinja2 서버 렌더링 (S00 결정, S05에서 의존성 추가)

## D-014 프로젝트 성격: 비상용 학부 프로젝트, 시연 가능한 완성본 (2026-10-04, 개발자 결정)
- 결정: 상용화하지 않는다. 총정리의 기능과 품질 원칙은 그대로 목표로 하되, 완료 기준은 "운영 서비스"가 아니라 "실제로 동작하는 시연 가능한 완성본"이다.
- DB: 개발·테스트는 PC에 설치한 PostgreSQL, 시연용 배포는 Supabase 무료 플랜(PostgreSQL을 대신 운영해 주는 서비스). 코드는 같고 `DATABASE_URL`만 다르다. Supabase의 인증·API 기능은 쓰지 않는다(D-005 보완). 로컬 PostgreSQL 주 버전은 Supabase 프로젝트와 맞춘다.
- 서비스화 전 확인 항목(기상사업자 등록, 상업적 이용 조건, 상표)은 상용화할 때만 필요하므로 작업을 막지 않는다. 판단 보조 문구는 계속 표시한다.

## D-015 카카오 알림톡은 구조만 두고 실제 발송은 사업자 등록 후 (2026-10-04, 개발자 결정)
- 결정: S06은 발송 어댑터 구조, 발송 이력·재시도·중복 방지, 알림 문구 생성까지 구현한다. 발송은 미리보기 어댑터(메시지를 발송 이력에 저장하고 웹에서 확인)로 동작시킨다.
- 알림톡 어댑터는 만들지 않고, 화면에 "카카오톡 발송은 사업자 등록 후 제공"으로 표시한다. 알림톡은 사업자 등록과 비즈니스 채널이 필요한 것으로 알고 있음 `[미확인: 정확한 요건]`.
- 이유: 비상용 프로젝트(D-014)에서 사업자 등록 없이 진행하되, 나중에 어댑터 하나만 추가하면 실제 발송이 되도록 경계를 유지한다.

## D-016 화면 먼저, 기능은 나중에 연결 (2026-10-04, 개발자 결정)
- 결정: 화면 시안(4개: 대시보드·판정 상세·판정 내역·현장 설정)을 예시 데이터로 먼저 서버 렌더링 화면으로 만들고, 판정·예보·DB는 이후 작업(S01~S04)에서 `service.py`만 교체해 연결한다. 이 화면 작업을 S05-0으로 둔다.
- 이유: 개발자가 결과를 눈으로 보며 방향을 확인하려는 요구. 화면 구조(템플릿·CSS·라우트)는 이후에도 그대로 쓰이므로 버리는 코드가 적다.
- 조건: 모든 화면에 "예시 데이터"를 표시하고, 저장·발송처럼 아직 없는 기능은 눌러도 동작하지 않게 막고 이유를 적는다. 예시의 기준값·기준 버전은 `원문 대조 필요`를 유지한다. 판정 4단계 이름·판단 보조 문구는 그대로 쓰고 `공온지수`는 표시하지 않는다.
- 의존성: `jinja2` 추가(D-004).

## D-017 화면의 공종을 총정리 목록 7개로 확장 (2026-10-04, 개발자 요청)
- 결정: 현장 설정·대시보드·판정 내역·알림 미리보기(예시 데이터)에 총정리의 공종을 모두 넣는다. §1 기준 표의 철골 작업·타워크레인 운전·콘크리트 타설은 `원문 대조 필요`, §3 4단계의 이동식 크레인·고소작업대·도장·방수·아스팔트 포장은 `기준 미확인`으로 표시한다. 총정리에 없는 공종(토공·거푸집 등)은 넣지 않는다.
- 판정 표시: `기준 미확인` 공종은 `확인 필요`까지만 낸다(근거 없는 `진행`·`중지 검토` 금지). 타워크레인은 기준이 순간풍속이라 예보 평균 풍속과 직접 비교할 수 없어 `확인 필요`. 콘크리트는 §1의 기온 기준만 비교한다.
- 범위: 화면 예시만 바꿨다. 판정 엔진(S01·S03)은 그대로 철골부터이며, 다른 공종의 기준 원문 대조·규칙 구현을 첫 출시에 넣을지는 개발자가 정한다(`docs/plan.md` 첫 출시 범위의 "제외" 항목).
- 폭염(체감온도)은 공종이 아니라 공통 조건이라 공종 목록에 넣지 않았다.

## D-018 판정 방식 초안 (S01·S03, 원문·활용가이드 대조 전)
- 구간 판정: 작업 시간에 걸친 정시 예보마다 조건을 비교하고, 시간·구간 판정은 가장 높은 단계. 단계 순서 `진행 < 확인 필요 < 판정 불가 < 중지 검토` — 기준을 넘은 시각이 있으면 다른 시각의 누락보다 중지 검토가 우선하고, 누락이 있으면 '진행'이라고 말할 수 없으므로 판정 불가가 확인 필요보다 높다.
- 예보 시각 h는 h:00~h+1:00을 대표한다고 본다. 작업 시작이 정각이 아니면 그 시각이 든 정시를 포함한다. `[확인 필요: 활용가이드의 PCP 1시간 강수량 시각 정의]`
- 범주 예보(PCP "1mm 미만", "30.0~50.0mm" 등)는 구간으로 비교한다. 구간 전체가 기준에 해당하면 기준의 판정, 전체가 미만이면 진행, 기준값에 걸치면 확인 필요(넘는다고 단정하지 않음).
- 누락(요소 없음·±900 결측·해석 불가 값·예보 없는 시각)은 판정 불가. `forecast_comparable: false` 조건은 값과 무관하게 확인 필요.
- 시각: KST는 고정 오프셋 `+09:00`(`engine/kst.py`). D-008의 택일.
- 기준표 `rules/steel.yaml`은 총정리 §1 값을 옮긴 초안이다(`source_verified: false`, 원문 인용 없음). 화면에 "원문 대조 필요"를 계속 표시한다.

## D-019 로그인 없는 기본 흐름을 먼저 완성 (2026-10-04, 개발자 결정)
- 결정: 회원·로그인(S04-2)과 알림 발송(S06)을 빼고, 현장 등록 → 예보 수집 → 철골 판정 → 대시보드·상세·내역까지 실제 DB로 동작하게 만든다. 1인 사용 전제라 현장별 접근 권한 검사가 없다(S04-2에서 추가).
- 브랜치: `feature/S04-basic-app` 하나에서 S01 초안·S02-2·S03·S04-1·S04-3·S04-4·S05를 하위 작업 커밋으로 진행했다(개발자 요청 범위가 여러 작업에 걸침).
- 예시 데이터(`sample.py`)는 지웠다. 화면 구조·문구(S05-0)는 그대로 쓰고 데이터만 DB로 바꿨다.
- 판정은 사용자가 대시보드에서 '지금 판정하기'를 눌러 실행한다. 매일 17시 자동 실행은 S06.
- 위치는 위경도 직접 입력(주소 → 좌표 변환 API 없음). 주소는 메모로만 저장한다.
- 예보 수집 기록은 `app/features/forecasts/`(수집 1회 = `forecast_runs` 1행, 원자료 JSONB 보관). 같은 발표 시각·격자의 성공 수집은 부분 고유 인덱스로 하나만, 실패는 시도마다 남기고 재사용하지 않는다.

## D-020 기상청 호출은 표준 라이브러리 urllib, 의존성 추가 (S02-2·S04, D-007 미정 해소)
- HTTP: `urllib.request`. 요청이 하나뿐이라 클라이언트 의존성을 늘리지 않는다. 호출 함수(`HttpGet`)를 인자로 받아 테스트에서 가짜로 바꾼다.
- 의존성 추가: `sqlalchemy`, `alembic`, `psycopg[binary]`(D-005), `pyyaml`(기준표), `python-multipart`(HTML 폼), 개발용 `types-pyyaml`.
- `alembic.ini`는 ASCII만 쓴다(한국어 Windows에서 Alembic이 cp949로 읽어 실패). 실행은 `python -m alembic`(한글 경로 trampoline 문제).
- 테스트 DB: `TEST_DATABASE_URL`(이름에 `test` 필수 — 스키마를 지우고 마이그레이션을 다시 적용한다). CI는 `postgres:17` 서비스로 DB 테스트를 실행한다. 로컬 검증은 설치 없는 임시 PostgreSQL 16.2(pgserver, 프로젝트 의존성 아님)로 했다.

## D-027 타워크레인·폭염 판정 추가 (S01-2·S01-3, 2026-10-07, 개발자 요청 묶음 A)

## D-030 강수량·적설 예보 시각은 두 해석 모두 비교 (S03, 2026-10-08)
- 확인한 공식 자료: 단기예보 조회서비스 활용가이드 DOCX(260928, ZIP SHA256 `437f3b92…`), 기상청 기상기후데이터위키 단기예보, 날씨누리 예보발표안내. PCP·SNO를 "1시간 강수량", "1시간 신적설"이라고만 하고, 예보 시각 h의 값이 h-1~h인지 h~h+1인지는 어디에도 정의하지 않는다. D-018의 `[확인 필요]`는 문서로 해소되지 않는다.
- 결정: 누적값(PCP·SNO)은 작업 칸 h~h+1을 h 예보(h~h+1 해석)와 h+1 예보(h-1~h 해석) 둘 다로 판정한다. 둘이 같으면 그 판정, 다르면 `확인 필요`로 두고 사유에 두 값을 함께 적는다. h 예보가 없으면 그대로 `판정 불가`이고, 다음 시각 값으로 누락을 메우지 않는다. 순간값(풍속·기온·습도·체감온도)은 기존대로 h 예보만 쓴다.
- 이유: 정의가 없는데 한쪽을 고르면 비가 오는 1시간을 통째로 놓칠 수 있다. 반대로 한쪽만 기준에 해당할 때 `중지 검토`로 올리면 근거 없이 단정하게 된다(AGENTS 품질 원칙). 비는 대개 여러 시간 이어지므로 강우 한가운데는 두 해석 모두 `중지 검토`가 되고, 비의 시작·끝 경계 1시간만 `확인 필요`가 된다.
- 영향: 같은 예보라도 이전보다 강우 시작 직전·종료 직후 칸이 `확인 필요`가 될 수 있다. 계약 형식(schema v1.1)은 바뀌지 않았다. 2026-10-08 이전에 저장된 판정은 h 예보만 쓴 결과다. 기상청이 정의를 공개하면 한 해석으로 좁히고 이 결정을 갱신한다.

## D-033 콘크리트 타설 기준과 하루 단위 기온 (S01-4, 2026-10-08)
- 확보한 공식 원문: KCS 14 20 41:2025 서중콘크리트(CODIL 고시 PDF), 국토교통부 「강우 시 콘크리트 타설을 위한 가이드라인」(2024.12, CODIL). 발췌와 PDF 해시는 `rules/sources/kcs_concrete.json`.

- 한중(KCS 14 20 40): 원문을 국가건설기준센터에서만 받을 수 있어(브라우저 전용) 확보하지 못했다. 2차 자료의 "일평균기온 4℃ 이하"를 `확인 필요`로만 넣고, 기준표 전체를 `source_verified: false`(화면에 원문 대조 필요)로 둔다. 추운 날 콘크리트가 근거 없이 `진행`으로 나오는 것을 막기 위해서다. 원문을 받으면 이하/미만·24시간 최저 0℃ 조건까지 대조하고 검증 완료로 바꾼다.
