## D-001 저장소 위치 (S00, 2026-10-04)
- 결정: 요구사항 MD가 있던 `%USERPROFILE%\OneDrive\바탕 화면\새 폴더`를 저장소 루트로 사용. 기존 MD는 위치·내용을 바꾸지 않는다(커밋 범위는 D-009).
- 이유: 기존 코드가 없고, 작업 폴더로 열려 있던 위치다. 두 도구가 같은 경로를 연다.
- 영향·주의: OneDrive 동기화 폴더라 `.venv`·`.git`이 동기화되고 파일 잠금이 생길 수 있다. 문제가 생기면 동기화되지 않는 경로(예: `C:\dev\...`)로 폴더째 옮기고 `docs/handoff.md`의 저장소 경로를 갱신한다(이동은 개발자가 결정).

## D-002 실행 환경: Python 3.12 + uv (S00)
- 결정: Python 3.12(`.python-version`), 의존성 관리 uv, 잠금 파일 `uv.lock`. `[tool.uv] package = false`로 저장소 루트에서 `engine`·`app`을 import한다.
- 이유: 잠금 파일 하나로 두 도구·CI가 같은 버전을 쓴다. 단일 앱이라 배포 패키지 빌드가 필요 없다.

## D-014 프로젝트 성격: 비상용 학부 프로젝트, 시연 가능한 완성본 (2026-10-04, 개발자 결정)
- 결정: 상용화하지 않는다. 총정리의 기능과 품질 원칙은 그대로 목표로 하되, 완료 기준은 "운영 서비스"가 아니라 "실제로 동작하는 시연 가능한 완성본"이다.
- DB: 개발·테스트는 PC에 설치한 PostgreSQL, 시연용 배포는 Supabase 무료 플랜(PostgreSQL을 대신 운영해 주는 서비스). 코드는 같고 `DATABASE_URL`만 다르다. Supabase의 인증·API 기능은 쓰지 않는다(D-005 보완). 로컬 PostgreSQL 주 버전은 Supabase 프로젝트와 맞춘다.
- 서비스화 전 확인 항목(기상사업자 등록, 상업적 이용 조건, 상표)은 상용화할 때만 필요하므로 작업을 막지 않는다. 판단 보조 문구는 계속 표시한다.

## D-015 카카오 알림톡은 구조만 두고 실제 발송은 사업자 등록 후 (2026-10-04, 개발자 결정)
- 결정: S06은 발송 어댑터 구조, 발송 이력·재시도·중복 방지, 알림 문구 생성까지 구현한다. 발송은 미리보기 어댑터(메시지를 발송 이력에 저장하고 웹에서 확인)로 동작시킨다.
- 알림톡 어댑터는 만들지 않고, 화면에 "카카오톡 발송은 사업자 등록 후 제공"으로 표시한다. 알림톡은 사업자 등록과 비즈니스 채널이 필요한 것으로 알고 있음 `[미확인: 정확한 요건]`.
- 이유: 비상용 프로젝트(D-014)에서 사업자 등록 없이 진행하되, 나중에 어댑터 하나만 추가하면 실제 발송이 되도록 경계를 유지한다.

## D-016 화면 먼저, 기능은 나중에 연결 (2026-10-04, 개발자 결정)
- 결정: 화면 시안(4개: 대시보드·판정 상세·판정 내역·현장 설정)을 예시 데이터로 먼저 서버 렌더링 화면으로 만들고, 판정·예보·DB는 이후 작업(S01~S04)에서 `service.py`만 교체해 연결한다. 이 화면 작업을 S05-0으로 둔다.
- 이유: 개발자가 결과를 눈으로 보며 방향을 확인하려는 요구. 화면 구조(템플릿·CSS·라우트)는 이후에도 그대로 쓰이므로 버리는 코드가 적다.
- 조건: 모든 화면에 "예시 데이터"를 표시하고, 저장·발송처럼 아직 없는 기능은 눌러도 동작하지 않게 막고 이유를 적는다. 예시의 기준값·기준 버전은 `원문 대조 필요`를 유지한다. 판정 4단계 이름·판단 보조 문구는 그대로 쓰고 `공온지수`는 표시하지 않는다.
- 의존성: `jinja2` 추가(D-004).

## D-017 화면의 공종을 총정리 목록 7개로 확장 (2026-10-04, 개발자 요청)
- 결정: 현장 설정·대시보드·판정 내역·알림 미리보기(예시 데이터)에 총정리의 공종을 모두 넣는다. §1 기준 표의 철골 작업·타워크레인 운전·콘크리트 타설은 `원문 대조 필요`, §3 4단계의 이동식 크레인·고소작업대·도장·방수·아스팔트 포장은 `기준 미확인`으로 표시한다. 총정리에 없는 공종(토공·거푸집 등)은 넣지 않는다.
- 판정 표시: `기준 미확인` 공종은 `확인 필요`까지만 낸다(근거 없는 `진행`·`중지 검토` 금지). 타워크레인은 기준이 순간풍속이라 예보 평균 풍속과 직접 비교할 수 없어 `확인 필요`. 콘크리트는 §1의 기온 기준만 비교한다.
- 범위: 화면 예시만 바꿨다. 판정 엔진(S01·S03)은 그대로 철골부터이며, 다른 공종의 기준 원문 대조·규칙 구현을 첫 출시에 넣을지는 개발자가 정한다(`docs/plan.md` 첫 출시 범위의 "제외" 항목).
- 폭염(체감온도)은 공종이 아니라 공통 조건이라 공종 목록에 넣지 않았다.

## D-018 판정 방식 초안 (S01·S03, 원문·활용가이드 대조 전)
- 구간 판정: 작업 시간에 걸친 정시 예보마다 조건을 비교하고, 시간·구간 판정은 가장 높은 단계. 단계 순서 `진행 < 확인 필요 < 판정 불가 < 중지 검토` — 기준을 넘은 시각이 있으면 다른 시각의 누락보다 중지 검토가 우선하고, 누락이 있으면 '진행'이라고 말할 수 없으므로 판정 불가가 확인 필요보다 높다.
- 예보 시각 h는 h:00~h+1:00을 대표한다고 본다. 작업 시작이 정각이 아니면 그 시각이 든 정시를 포함한다. `[확인 필요: 활용가이드의 PCP 1시간 강수량 시각 정의]`
- 범주 예보(PCP "1mm 미만", "30.0~50.0mm" 등)는 구간으로 비교한다. 구간 전체가 기준에 해당하면 기준의 판정, 전체가 미만이면 진행, 기준값에 걸치면 확인 필요(넘는다고 단정하지 않음).
- 누락(요소 없음·±900 결측·해석 불가 값·예보 없는 시각)은 판정 불가. `forecast_comparable: false` 조건은 값과 무관하게 확인 필요.
- 시각: KST는 고정 오프셋 `+09:00`(`engine/kst.py`). D-008의 택일.
- 기준표 `rules/steel.yaml`은 총정리 §1 값을 옮긴 초안이다(`source_verified: false`, 원문 인용 없음). 화면에 "원문 대조 필요"를 계속 표시한다.

## D-019 로그인 없는 기본 흐름을 먼저 완성 (2026-10-04, 개발자 결정)

- 브랜치: `feature/S04-basic-app` 하나에서 S01 초안·S02-2·S03·S04-1·S04-3·S04-4·S05를 하위 작업 커밋으로 진행했다(개발자 요청 범위가 여러 작업에 걸침).
- 예시 데이터(`sample.py`)는 지웠다. 화면 구조·문구(S05-0)는 그대로 쓰고 데이터만 DB로 바꿨다.
- 판정은 사용자가 대시보드에서 '지금 판정하기'를 눌러 실행한다. 매일 17시 자동 실행은 S06.
- 위치는 위경도 직접 입력(주소 → 좌표 변환 API 없음). 주소는 메모로만 저장한다.
- 예보 수집 기록은 `app/features/forecasts/`(수집 1회 = `forecast_runs` 1행, 원자료 JSONB 보관). 같은 발표 시각·격자의 성공 수집은 부분 고유 인덱스로 하나만, 실패는 시도마다 남기고 재사용하지 않는다.

## D-020 기상청 호출은 표준 라이브러리 urllib, 의존성 추가 (S02-2·S04, D-007 미정 해소)
- HTTP: `urllib.request`. 요청이 하나뿐이라 클라이언트 의존성을 늘리지 않는다. 호출 함수(`HttpGet`)를 인자로 받아 테스트에서 가짜로 바꾼다.
- 의존성 추가: `sqlalchemy`, `alembic`, `psycopg[binary]`(D-005), `pyyaml`(기준표), `python-multipart`(HTML 폼), 개발용 `types-pyyaml`.
- `alembic.ini`는 ASCII만 쓴다(한국어 Windows에서 Alembic이 cp949로 읽어 실패). 실행은 `python -m alembic`(한글 경로 trampoline 문제).
- 테스트 DB: `TEST_DATABASE_URL`(이름에 `test` 필수 — 스키마를 지우고 마이그레이션을 다시 적용한다). CI는 `postgres:17` 서비스로 DB 테스트를 실행한다. 로컬 검증은 설치 없는 임시 PostgreSQL 16.2(pgserver, 프로젝트 의존성 아님)로 했다.

## D-027 타워크레인·폭염 판정 추가 (S01-2·S01-3, 2026-10-07, 개발자 요청 묶음 A)

## D-030 강수량·적설 예보 시각은 두 해석 모두 비교 (S03, 2026-10-08)
- 확인한 공식 자료: 단기예보 조회서비스 활용가이드 DOCX(260928, ZIP SHA256 `437f3b92…`), 기상청 기상기후데이터위키 단기예보, 날씨누리 예보발표안내. PCP·SNO를 "1시간 강수량", "1시간 신적설"이라고만 하고, 예보 시각 h의 값이 h-1~h인지 h~h+1인지는 어디에도 정의하지 않는다. D-018의 `[확인 필요]`는 문서로 해소되지 않는다.
- 결정: 누적값(PCP·SNO)은 작업 칸 h~h+1을 h 예보(h~h+1 해석)와 h+1 예보(h-1~h 해석) 둘 다로 판정한다. 둘이 같으면 그 판정, 다르면 `확인 필요`로 두고 사유에 두 값을 함께 적는다. h 예보가 없으면 그대로 `판정 불가`이고, 다음 시각 값으로 누락을 메우지 않는다. 순간값(풍속·기온·습도·체감온도)은 기존대로 h 예보만 쓴다.
- 이유: 정의가 없는데 한쪽을 고르면 비가 오는 1시간을 통째로 놓칠 수 있다. 반대로 한쪽만 기준에 해당할 때 `중지 검토`로 올리면 근거 없이 단정하게 된다(AGENTS 품질 원칙). 비는 대개 여러 시간 이어지므로 강우 한가운데는 두 해석 모두 `중지 검토`가 되고, 비의 시작·끝 경계 1시간만 `확인 필요`가 된다.
- 영향: 같은 예보라도 이전보다 강우 시작 직전·종료 직후 칸이 `확인 필요`가 될 수 있다. 계약 형식(schema v1.1)은 바뀌지 않았다. 2026-10-08 이전에 저장된 판정은 h 예보만 쓴 결과다. 기상청이 정의를 공개하면 한 해석으로 좁히고 이 결정을 갱신한다.

## D-041 주간 판정은 최대 7일, 신뢰도는 자료 촘촘함으로 표시 (S08-3, 2026-10-08)
- 개발자 요청: 내일만이 아니라 앞으로의 막히는 날을 미리 본다. 범위는 최대 7일(개발자 결정). 8일 뒤 이후는 기준 비교에 쓸 예보 정확도가 낮아 넣지 않는다.
- 판정 실행 한 번에 같은 단기예보로 내일~7일을 판정한다. 작업 시간에 예보 값이 하나도 없는 날은 판정·저장하지 않는다(예보 범위 밖). 값이 일부만 있으면(3시간 간격) 엔진대로 빈 시각은 `판정 불가`이며 3시간 값을 앞뒤 시각으로 늘려 쓰지 않는다.
- 실제 응답 확인(2026-10-08 17시 발표, 개발 DB): +1~+3일 1시간 24개, +4일 3시간 8개, +5일 00시 1개. 계획(D-031)의 "+4·+5일 3시간"과 달리 실질 판정은 +4일까지다.
- 신뢰도는 점수·%가 아니라 그날 판정에 쓴 예보의 시간별 값 유무로만 정한다: 작업 시간 전체에 값 있음 → 높음, 일부 → 보통, 없음 → 예보 없음. 실측 적중률(%)과 공온지수는 실제 결과(S10)가 쌓인 뒤 정의한다(brand.md §4 유지).
- 실행 결과에 `beyond_forecast`(작업일이 예보 범위 밖)를 더했다. 7일 모두 작업 기간 밖이면 예보를 받지 않는다(`out_of_period`). 실패는 가장 가까운 작업일에만 기록한다.
- 홈 '최근 판정'은 내일까지 대상만 보여 준다(미래 날짜 판정이 목록을 채우지 않게). 판정 내역 화면은 전체를 보여 준다.
- 머신러닝은 쓰지 않는다(규칙 기반·설명 가능 원칙). 실제 결과가 쌓이면 신뢰도 보정·작업중단 확률(S14) 참고에 한해 검토한다.
- 같은 날 화면 피드백: 홈 요약 순서 판정 전 → 판정 불가 → 중지 검토 → 확인 필요 → 진행(개발자 지정), 판정 버튼 아래 안내 문구 대신 "현장 N곳 판정하기", 달력 '내일로'는 라임 아이콘 버튼, 일정 상세의 작은 링크는 "내일 판정 보기" 버튼.

## D-042 단기예보 범위 밖 날짜는 중기예보를 참고로 표시 (S08-3-2, 2026-10-08)
- 개발자 결정: 무료 자료원(기상청 중기예보 조회서비스, 공공데이터포털 자동승인)을 쓴다. 같은 KMA_SERVICE_KEY로 실제 호출 성공(2026-10-08).
- 중기육상예보는 오전·오후 강수확률(%)과 날씨 문구뿐이고 풍속·강우량이 없다. 그래서 판정 내역에 저장하지 않고 주간 표에서 '참고'(점선 칸, 신뢰도 낮음)로만 보여 준다.
- 참고 단계: 날씨 문구에 활용가이드의 현상(비·소나기 → 강우, 눈 → 적설, 비/눈 → 둘 다)이 있고 공종 기준에 그 요소가 있으면 `확인 필요`, 아니면 `판정 불가`. '진행'·'중지 검토'는 내지 않는다. 강수확률에 임의 기준(%)을 두지 않는다. 오전·오후 시간 범위는 문서에 없어 그날 어느 쪽이든 현상이 있으면 그날에 적용한다.
- 현장 → 예보구역: 주소 첫 낱말(시·도)을 활용가이드 구역표로 대응. 강원은 둘째 낱말(시·군)이 xlsx 11D2(강원영동) 도시면 영동, 아니면 영서. 대관령은 평창군 지점이라 평창군은 영서. 시·도를 알 수 없으면 중기예보를 쓰지 않는다.
- 수집: 발표 06·18시. 최근 발표가 실패(아직 제공 전 등)하면 12시간 전 발표를 쓴다(제공 지연 시각은 문서에 없음). 같은 발표·구역 성공은 한 번만 받는다(mid_forecast_runs, 마이그레이션 0006). 실패는 시도마다 기록하고 판정 실행은 계속한다.
- 대시보드 상세 카드는 판정이 있는 첫 작업이 아니라 가장 높은 단계 작업을 먼저 보여 주고, '자세히 볼 작업' 칩으로 바꿀 수 있다(개발자 피드백: 철골만 뜬금없이 나옴).

## D-047 현장 주소: 우편번호 창 + 카카오 주소 검색으로 위경도 (S05, 2026-10-08 개발자 요청)
- 개발자 피드백: 공사 현장은 카카오맵에 장소로 등록되지 않아 키워드 검색(D-022)으로 안 나오고, 가게·장소 목록이 떠서 헷갈린다. 지번·도로명을 넣으면 위경도가 자동으로 나와야 하고, 회원가입 때 보던 주소 창이 익숙하다.
- 결정: 주소 칸 옆 [주소 찾기] = 다음 우편번호 서비스 창(키 불필요, 외부 스크립트 `t1.daumcdn.net/.../postcode.v2.js`). 고른 주소(사용자가 고른 도로명 또는 지번 → 실패 시 다른 쪽)를 서버 `/sites/places`가 카카오 로컬 '주소 검색하기'로 위경도로 바꾼다. 같은 `KAKAO_REST_API_KEY`, 추가 신청 없음. 키워드 장소 검색과 입력 중 자동 후보 목록은 없앴다.
- 우편번호 창에 없을 수 있는 빈 땅 지번은 주소 칸에 직접 입력하고 Enter로 같은 주소 검색을 한다. 후보가 여럿이면 주소 목록에서 고르고, 없으면 위경도 직접 입력(기존 경로 유지). 주소를 고쳐 쓰면 이전 위경도를 비워 다른 위치로 저장되지 않게 한다.
- 실제 호출(2026-10-08): 도로명 `서울 중구 세종대로 110`, 지번 `서울 중구 태평로1가 31` 각 1건, 도로명 없는 지번 `강원 평창군 대관령면 횡계리 1`도 좌표 반환(road_address null). 없는 지번은 0건. 좌표는 필지·건물 대표 지점이며 기상청 5km 격자 판정에는 충분하다.
- `[확인 필요]` 우편번호 창 선택 → 좌표 채움은 실제 브라우저에서 확인 전(자동 테스트 없음). 주소 검색 무료 쿼터는 문서 확인 전. D-022의 키워드 검색 결정을 대체한다.

## D-048 현장 주소는 도로명·지번 두 칸 (S05, 2026-10-08 개발자 요청)
- 개발자 요청: 주소 입력을 도로명·지번 두 칸으로. 공사 부지는 도로명이 없거나 지번으로만 알려진 경우가 많다.
- `sites.road_address`·`sites.lot_address`(빈 문자열 기본, 마이그레이션 0008). 둘 중 하나는 필수. 기존 `address`는 대표 주소(도로명 우선, 없으면 지번)로 남겨 예보구역 찾기·이름 대체·목록 표시에 그대로 쓴다.
- 기존 행 이전: 로/길 뒤에 띄우고 번호가 오면 도로명, 아니면 지번(`태평로1가 31` 같은 법정동 이름을 도로명으로 오인하지 않게 공백 요구). 개발 DB 4곳 모두 도로명으로 분류됨을 확인, 되돌리기·재적용 확인.
- 화면: [주소 찾기] 우편번호 창에서 고르면 두 칸을 모두 채우고, 카카오 주소 검색으로 위경도를 채운다. 한 칸만 입력하고 Enter면 그 칸으로 찾고 다른 칸은 검색 결과로 채운다(도로명 없는 땅은 빈칸). D-047의 한 칸 입력을 대체한다.

## D-049 화면 정리: 탭 머리 통일·색 줄이기·글자 정렬선·판정 내역 묶음 (S05-1, 2026-10-08 개발자 피드백)
- 글자 정렬선: 박스 바깥 글자는 둥근 박스 테두리와 박스 안 첫 글자의 가운데에 맞춘다(개발자 지정. 들여쓰기 = 안쪽 여백의 절반: `--head-inset`·`--label-inset`·`--inset/2`). 공통 CSS로 적용.
- 색: 넓은 면은 흰색·회색, 파랑은 행동·선택에만, 판정 색은 점·숫자·왼쪽 띠·배지에만(홈 요약 타일·공종 칩·판정 줄의 색 면 제거). D-045 팔레트 값은 그대로.
- 탭 머리: 모든 탭을 흰 대표 카드(배지 → 제목 → 설명/정보 칩, 오른쪽 행동)로 통일. 제목은 홈 '내일 공사 ON?', 대시보드 '{현장} 공사 ON?', 작업 일정 '{월} 공사 ON?'. 같은 정보를 두 번 쓰지 않는다(마지막 확인 시각은 데이터 상태에만).
- 판정 내역: 대상 날짜 카드 → 현장 소제목 → 판정 줄(판정·작업·예보/기준·›, 줄 전체 링크). 같은 날짜·현장·작업의 이전 예보 판정은 '이전 예보'로 흐리게. 조회 순서를 날짜·현장·최근 순으로 바꿔 한 쪽 안에서 묶음이 이어지게 했다(쪽 나눔은 판정 건수 기준 유지).
- 작업 일정: 달 제목을 누르면 연도별 달 목록(보고 있는 달 앞뒤 6개월 + 작업 기간, 작업 기간 달은 진한 글자, 내일이 든 달은 점). 서버 링크로 이동.
- 대시보드 위의 "← 전체 현장" 줄을 없애고 현장 선택·⋯ 메뉴를 대표 카드 오른쪽 위로 옮겼다(홈에서 넘어올 때 흐름 유지, 홈은 상단 메뉴로).
- 선택 상자는 같은 꺾쇠·여백, 툴바의 선택 상자는 알약형. 현장 삭제 영역의 버튼 세로 중앙 어긋남(닫힌 details의 gap) 수정.
- 판정·DB·계약 변경 없음. 1440px 캡처로 확인, 휴대폰 화면은 개발자 확인 필요.

## D-050 공온지수 v1: 7일 표의 날짜별 작업 가능 정도 (S08-5, 2026-10-08 개발자 결정)
- 개발자 결정: '신뢰도'를 공온지수로 바꾸고 일주일까지 보여 준다. 머신러닝 없이 규칙으로 계산한다(brand.md §4 조건 충족).
- 정의 `gongon-index-v1`(engine/judgment/index.py): 그날 판정한 작업들의 작업 시각마다 진행 100·확인 필요 50·중지 검토 0점의 평균(정수, 0.5 올림). 판정 불가 시각(예보 값 없음)은 넣지 않고, 비교한 시각이 없으면 점수 없음. 그날 가장 높은 단계로 상한: 확인 필요 70, 중지 검토 30(기준 미확인 공종의 확인 필요 포함) → 판정과 모순 없음.
- 범위: 내일~7일 표의 날짜 머리. 단기예보로 판정을 저장한 날(실제 +1~+4일)만 점수를 내고, 3시간 간격 날은 '일부 시각'으로 표시. +5~+7일 중기예보 참고 날은 기준과 직접 비교할 수 없어 점수를 내지 않고 '중기 참고'로 표시(누락·비교 불가에는 점수를 내지 않는 원칙). 판정 상세·알림·판정 내역에는 아직 표시하지 않는다.
- 예보 자료의 촘촘함(기존 '신뢰도')은 '예보 상세도'로 날짜 머리 설명(title)에만 남긴다. 설명은 제목 옆 '공온지수란?' 팝오버로 옮겼다.
- 저장: 점수는 저장된 판정(시각별 단계)과 코드의 버전 상수로 다시 계산한다. 현재 7일 화면에만 쓰므로 별도 저장하지 않았다. 판정 내역·보고서에 점수를 남기게 되면 계산식 버전과 함께 저장한다(brand.md §4).
- 테스트: tests/engine/judgment/test_index.py(평균·상한 경계·판정 불가 제외·점수 없음·반올림), test_week.py(날짜별 점수·중지 검토 30점 이하·일부 시각·중기 참고).

## D-052 공온지수 v2: 기준 여유·강수확률·예보 안정성 (S08-5, 2026-10-08 개발자 요청)
- 개발자: v1이 너무 단순하다, 예보 신뢰도를 토대로 구체화하라. 기상청은 예보마다 신뢰도 값을 주지 않으므로 받은 자료에서 근거를 댈 수 있는 것만 쓴다(engine/judgment/index.py, `gongon-index-v2`).
- 진행 시각도 아슬아슬하면 낮춘다: 기준까지 여유(기준 대비 %, '이상·초과'는 값 위쪽 끝, '이하'는 아래쪽 끝)가 10% 미만 70점, 20% 미만 85점. 비 기준이 있는 작업은 단기예보 강수확률(POP, 원자료 forecast_runs.raw_items)이 60% 이상 70점, 30% 이상 85점까지. 둘 중 낮은 값 하나만 적용.

- 테스트: tests/engine/judgment/test_index.py(여유·강수확률 경계, 한 번만 적용, 변경 감점, 상한, 반올림, 여유 계산).

## D-053 예보 간격이 성긴 날도 같은 날 값으로 판정 (S08-3, 2026-10-08 개발자 결정, D-041 변경)
- 개발자: 4일 뒤 3시간 간격·5일 뒤 00시 값뿐인 날도 그 값으로 작업 전체를 판단한다. 날짜가 가까워지면 매시간 예보로 갱신되고 대비할 시간이 있다.
- engine judge: 작업 시각 예보가 없으면 같은 현지 날짜의 가장 가까운 예보 시각 값으로 추정한다(같으면 이른 시각). 누적값의 h+1 해석(D-030)도 같은 방식. 다른 날 값은 쓰지 않는다(그날 값이 없으면 판정 불가).

## D-054 화면 정리 2 (S05-1·S08, 2026-10-08 개발자 요청)
- 판정 내역: 삭제한 현장의 판정은 목록·건수에서 뺀다(DB 기록 유지, 상세 주소는 열림, D-040 보완). 메뉴의 판정 내역은 늘 전체 현장. 필터 줄 오른쪽 '총 N건 중 a–b · [N개씩] · [전체 현장]', 아래는 쪽 번호만.
- 대시보드: 공종별 판정 줄을 누르면 그 작업의 단계별 시간·구간·시간대별 예보 그래프 모달(머리에 상세 근거, 아래 닫기). 아래 따로 있던 '자세히 볼 작업'·그래프 카드는 없앴다. 대표 카드 오른쪽은 현장 선택·⋯·다시 판정하기 한 줄.
- 작업 일정: 작업 추가는 버튼 → 모달. 공종·시간 기본값 없음, 빈칸이면 저장 안 됨. 작업 날짜는 모달 안 달력에서 여러 날을 눌러 고르고(칩), 날마다 같은 시간으로 한 번에 저장(최대 31일, 하나라도 맞지 않으면 아무것도 저장 안 함). 작업 카드는 작업명 → 시간·위치 → 메모.
- 성공 안내는 화면 아래 토스트(4초 뒤 사라짐), 오류 안내는 화면에 남는다. 모달은 바깥·Esc·닫기로 닫힌다.


## D-055 작업 변경 후속 조치 중심 재기획 (C00, 2026-10-16 사용자 요청)

- 사용자 요청: 대형 건설사 프로젝트, 원청 아래 여러 협력업체·의사결정자 공동 사용, 기상을 포함한 공사 전반 요인. 기존 범용 협업 제품의 하위호환 우려를 반영해 작업 변경 후속 조치 연결·실제 완료 확인을 첫 상품으로 재기획한다.

- 핵심 동작: 확정 버전별 조치·수행자·검증자·기한·근거. 전송·열람·응답·완료 보고·검증을 구분하고 현재 필수 조치가 남으면 종료하지 않는다. 재변경은 새 버전·대체·보완 조치로 처리한다. 외부 예약의 자동 변경·원복을 주장하지 않는다.

- 자료 변경의 재검토(C09), 현장 간 자원 연결(C10)은 후속 수요 확인 뒤 선택한다. 제품 내 LLM·자동 발주/예약 취소·새 종합 점수는 첫 범위에 없다.
- 기획 설계안: 기존 Site·WorkItem·기상 엔진을 재사용하고 변경·조치·발송 대기의 원자적 저장·권한·버전을 검증한다. 세부 계약·DB는 해당 작업에서 확정하며 이번 C00은 코드·DB·기상 JSON을 변경하지 않는다.
- D-014 비상업 시연·D-015 실제 알림톡 조건은 유지한다. 계정·비용·원문·고객 전결과 취소 마감은 지어내지 않는다. 기상 판정 4단계·원문 대조·D-052 지수의 모듈 범위도 유지한다.

## D-056 공개 자료·합성 사례로 구현 진행 (C00-1, 2026-10-16 사용자 결정)

- 사용자는 학부생으로 실제 건설사 내부 자료·현장 인터뷰를 확보하기 어렵다고 설명했고, 현재 기획대로 개발을 진행하기로 했다. 실제 자료 확보를 구현의 필수 선행조건으로 두지 않는다.
- D-055 중 실제 자료가 없으면 C02 초안까지만 가능하다는 제한을 대체한다. C01은 공식 공개 자료·공개 사례·서식·경쟁 제품 조사, C02는 명시한 합성 시나리오·구현 계약 확정, C03~C07은 비상업 시연 구현으로 진행한다.
- 공개 조사 완료와 시장성·현장 효과 검증은 구분한다. 실제 반복 사용·입력 절감·지불 의사·구매 경로는 미검증으로 남기고 C08의 현장 시험에서 확인한다. 공개 문서에서 찾지 못한 경쟁 기능을 없다고 단정하지 않는다.
- 일반적인 구현 선택은 추천안을 정해 기록한다. 실제 계정·비용·기준 원문·고객의 실제 권한·기한은 지어내지 않는다. 합성 시연 자료를 실제 API 응답·내부 자료·시장 검증으로 표시하지 않는다.
- 이번 C00-1은 MD·PDF·인계 동기화다. 앱·DB·기상 판정 계약·기존 S작업 상태는 변경하지 않는다. D-014·D-015, 권한·원문 대조·검증 원칙을 유지한다.

## D-057 시연용 협업 계약과 인증 방식 (C02, 2026-10-16)

- 계약 원문: `docs/collab-contract.md`. C01 설계 가정 A1~A7과 합성 시나리오로 정한 시연 계약이며 고객 확인 계약이 아니다(D-056).
- 역할 3개(조정자·담당자·열람자). 조정자는 원청(prime) 소속만, 변경 확정·현장 수정·참여자 관리는 조정자만. 이유: 산안법 §64의 도급인 조정 역할(2차 확인)과 정합하고, 가장 단순한 시연 구조. 실제 전결 구조는 C08에서 확인.
- 자기 검증 금지(검증자 ≠ 완료 보고자)를 기본으로 한다. 고객 정책 확인 전 예외를 만들지 않는다.
- 인증: 이메일+비밀번호, `hashlib.scrypt`(표준 라이브러리, 새 의존성 없음). 서버 세션 테이블에 토큰 SHA-256만 저장, 쿠키 HttpOnly·SameSite=Lax, 만료 12시간. 외부 로그인(카카오 등)은 계정·사업자 조건이 필요해 제외.
- 요청 위조 방지: SameSite=Lax 쿠키 + 쓰기 요청의 Origin(없으면 Referer) 같은 출처 검사. 둘 다 없는 POST는 거부. 폼 토큰 방식보다 기존 템플릿·테스트 변경이 적고, 현행 브라우저는 폼 POST에 Origin을 보낸다. 다른 출처에서 쓰는 API가 생기면 토큰 방식을 다시 검토한다.
- 권한 실패는 비참여 404·역할 부족 403. 화면에서 숨기는 것으로 대신하지 않고 서비스 조회 조건에 멤버십을 넣는다.
- 기존 현장 행에는 참여 업체를 추정해 만들지 않는다. 개발자가 `scripts/grant_site.py`로 명시 지정한다.
- 초대 메일·링크는 만들지 않는다(실제 발송 조건 D-015). 가입된 사용자를 이메일로 추가한다. 위임·첨부 접근은 대상이 생기는 C06에서 같은 정책으로 구현한다.

## D-058 작업 숨김 삭제와 재판정 필요 표시 (C04-1, 2026-10-16)

- 작업 일정 삭제는 `work_items.deleted_at` 숨김 처리다(0011). 행을 지우면 판정의 작업 연결이 NULL이 돼 같은 공종·시간 작업 판정이 재사용 키에서 겹쳤다(S08-4-2). 현장 삭제(D-040)와 같은 방식이며 판정과 당시 작업의 연결을 보존한다. 화면 문구 "삭제한 일정은 되돌릴 수 없습니다"는 화면 복구 기능이 없다는 뜻으로 유지한다.
- 화면의 현재 판정은 저장된 판정의 격자·작업 시각·기준 버전이 지금 현장·작업·기준과 같을 때만이다. 다르면 단계 없이 "재판정 필요 · ○○ 변경 후 아직 판정하지 않음"을 보인다. 판정 4단계에 새 단계를 더하지 않는다. 홈 타일에서는 "판정 전"에 함께 센다.
- 작업별 최신 판정은 DB에서 (현장·날짜·공종·작업 ID)마다 먼저 고른다. 주간 보기는 예보 발표별 최신 판정 중 최근 2개(공온지수 예보 안정성용)를 읽는다. 개수 제한 후 묶는 방식은 쓰지 않는다.
- 7일 표의 예보 상세도: 추정 시각(D-053, 엔진 `ESTIMATED_NOTE`)이 있는 날은 값이 있어도 "보통"이다. 판정 계약(schema.json)에는 추정 여부 필드를 더하지 않았다. 필요해지면 계약 버전을 올려 구조화한다.

## D-059 공종·작업 시간은 작업마다, 폭염은 작업 카드에 합침 (C04-3, 2026-10-16 개발자 결정)

- 개발자: 작업을 등록하면 현장 주요 공종이 판정에서 빠지므로 현장 설정에서 정할 이유가 없다. 현장 설정에서 주요 공종·기본 작업 시간을 빼고 작업 관리를 편하게 한다. 폭염은 공통 기준이니 따로 보이지 말고 녹여 넣는다.
- 현장 설정은 위치·작업 기간만. 0013에서 sites.work_types·work_start_local·work_end_local의 NOT NULL을 풀고 값은 남겨 둔다(과거 판정은 공종 이름·작업 시각을 판정 행에 따로 저장해 영향 없음).
- D-023의 "작업이 없는 내일은 현장 기본 공종으로 대체 판정"을 대체한다. 작업이 있는 날만 판정하고, 판정할 작업이 없으면 예보를 받지 않는다(`no_work`).
- 폭염(공통)은 작업마다 그 작업 시간으로 판정해 저장한다(키 `item:<id>:폭염(공통)`). 화면은 작업 카드 하나에 합쳐, 폭염이 더 높은 단계면 그 단계·"폭염 · 사유"·상세를 보인다. 같은 단계면 작업 쪽을 보인다. 기준 미확인 공종은 폭염 판정을 상세로 연다. 따로 폭염 카드·주간 줄을 두지 않는다.
- 작업 추가 편의: 공종 여러 개를 칩으로 한 번에(공종 × 날짜마다 작업 하나), 이 현장에서 많이 쓴 공종을 앞에, 날짜는 하나씩 또는 기간+요일(기본 월~금 선택, 최대 92일), 최근 쓴 시간은 버튼으로만(미리 채우지 않음, 기존 "시간 기본값 없음" 유지), 작업 카드의 "다른 날에도 추가"(같은 내용으로 열고 날짜만 다시 고름), 저장 전 건수 표시. 한 번에 100건까지, 하나라도 맞지 않으면 아무것도 저장하지 않는다.

## D-060 변경 건·확정 구현 선택 (C05, 2026-10-16)

- 제안은 조정자·담당자, 확정은 조정자만(D-057). 담당자는 자기 제안만 영향 검토로 보내거나 철회한다. 열람자는 보기만.
- 변경 내용은 작업의 날짜·시작·종료·위치다. 메모·실행 업체는 변경 확정으로 바꾸지 않고(작업 계획 수정에서 바꿈) 그대로 둔다. 공종은 바꾸지 않는다(새 작업).
- 바뀐 날짜는 오늘도 허용한다(긴급 변경 기록). 지난 날짜·작업 기간 밖은 거부한다. 기존 작업 추가의 "내일 이후" 규칙과 다르다.
- 확정은 제안 당시 계획 버전(based_on_plan_version)과 지금 버전이 같을 때만 한다. 다르면 확정하지 않고 철회 뒤 새 제안을 안내한다(자동 재기준 없음).
- 같은 확정 요청 재전송은 화면마다 새로 만드는 confirm_key로 알아보고 "이미 확정"으로 답한다. 버전 행은 확정·철회 때 FOR UPDATE로 잠근다. 한 건의 진행 중 버전 하나·현재 확정 버전 하나는 부분 고유 인덱스(0014)가 강제한다.
- 확정 트랜잭션은 계획 갱신(작업 변경 이력 source='change')·이전 확정 버전 superseded·이 버전 confirmed다. 후속 조치(C06)·발송 대기(C07)는 `changes.service._after_confirm`에 같은 트랜잭션으로 더한다. 변경 건 종료(closed_at)는 조치가 생기는 C06에서 구현한다.
- 목록은 최근 50건(진행 중/전체). 더 필요해지면 페이지 처리를 더한다.

## D-061 오늘 작업 등록·날짜/시간 고르기 (C04-4, 2026-10-16 개발자 요청)

- 공정 관리 앱은 오늘 작업을 볼 수 있고 등록할 수 있어야 한다(개발자). 작업 추가·수정의 날짜 규칙을 "내일 이후"에서 "오늘 이후"로 바꾼다(D-036의 날짜 규칙을 대체, D-060 변경 제안과 같은 기준). 지난 날짜·작업 기간 밖은 계속 거부한다.
- 기상 판정 범위는 그대로 내일부터 7일(D-041)이다. 오늘 작업은 일정·변경 관리 대상이며 판정하지 않는다고 화면에 적는다. 오늘 판정이 필요하면 별도 작업으로 정한다(예보 시각·이미 지난 시간 처리 기준이 필요).
- 작업 일정 화면은 처음 열 때 오늘을 고른다. 달력의 "내일" 바로가기는 "오늘"로 바꿨다. 판정 대상(내일) 표시는 유지한다.
- 날짜·시간 입력은 브라우저 기본 입력 대신 공통 고르기 판(`app/core/static/picker.js`)을 쓴다. 날짜는 일 → 월 12칸 → 연 12칸, 시간은 시 24칸 + 분 5분 단위. 값 형식(YYYY-MM-DD·HH:MM)과 서버 검증은 바꾸지 않으며 스크립트가 없으면 기본 입력이 그대로 보인다. 5분보다 잘게는 고를 수 없다(현장 작업 시간 기록에 충분하다고 판단).

## D-062 홈은 오늘 작업 먼저, 내일 판정은 그 아래 (C04-5, 2026-10-16 개발자 요청)

- 현장 담당자가 아침에 홈을 열면 먼저 "오늘 어느 현장에서 무엇을 언제 누가 하는가"를 본다. 홈 첫 영역을 오늘 작업(현장별·시작 시각 순·실행 업체·위치)으로 바꾸고, 기존 내일 판정 요약·현장별 카드는 "내일 준비" 제목 아래로 옮겼다. 일괄 판정 버튼·예보 발표 정보도 그 제목 옆으로 옮겼다.
- 오늘 작업마다 지금 시각(KST) 기준 단계를 붙인다: 시작 전 `예정`, 시작 시각 이상·끝 시각 미만 `진행 중`, 끝 시각 이상 `끝남`. 이것은 계획 시간 기준 표시이며 실제 작업 결과 기록(S10)이 아니다. 실제 진행·중단은 자동으로 만들지 않는다(총정리 §1.3).
- 오늘 작업은 기상 판정을 하지 않는다(D-061 유지). 내일 판정 영역의 "내일 공사 ON?" 질문은 홈 머리 대신 대시보드에 남는다.

## D-063 주 메뉴 4개와 공온 말투 (C04-6, 2026-10-16 개발자 요청)

- 주 메뉴가 6개(홈·현장 대시보드·작업 일정·변경·판정 내역·현장 설정)라 하위 기능까지 맨 위에 올라와 있었다(개발자). 현장 담당자가 매일 쓰는 핵심 4개 **홈·작업 일정·변경·현장**만 남긴다.
- 기상 판정은 작업 일정을 정하는 근거라서 작업 일정 안의 하위 메뉴 **달력·공온 판정·판정 내역**으로 옮겼다(주소 `/schedule`·`/dashboard`·`/judgments`는 그대로). 참여자 화면은 현장 안에 둔다(기존 그대로).
- 화면 머리 설명을 공온이 주어인 한 문장으로 맞췄다(brand.md “공온 말투”). 작업 일정 제목의 “공사 ON?”은 작업 허가처럼 읽혀 “작업 일정”으로 바꾸고, “공사 ON?”은 대시보드 질문으로만 남겼다.

## D-064 작업 일정·홈 리디자인, 설명은 가이드로 (C04-7, 2026-10-16 개발자 피드백)

- 작업 추가 모달: 공종은 같은 너비 2열 카드(공종 색 점), 날짜는 한 달 달력 하나에서 누르기·끌기로 여러 날을 고르고 바로가기(오늘·내일·이번 주 평일·다음 주 평일)를 둔다. ‘하나씩/기간+요일’ 전환은 없앴다(서버의 기간 입력은 그대로 받음). 시간은 구글 캘린더처럼 직접 치거나 30분 간격 목록에서 고르고, 종료 목록에는 걸리는 시간을 보이며 시작을 바꾸면 길이를 유지한다.
- **오늘 작업은 지금 이후 시작만** 등록한다(개발자). 같은 분은 이미 시작한 것으로 보고 거부한다. 이미 시작한 오늘 작업을 수정할 때 시작 날짜·시각을 그대로 두면 이 규칙을 다시 묻지 않는다(끝 시각 연장 가능).
- 공종마다 고정 색(`app/core/templating.WORK_TYPE_COLORS`, 판정 4단계 색과 겹치지 않게). 달력 칸에는 글 대신 공종 색 점(최대 5개 + 나머지 수)을 두고, 점을 누르면 그 작업 상세 모달이 열린다. 아래에 공종 색 범례.
- 날짜·달을 눌러도 페이지를 새로 띄우지 않고 달력·상세만 바꿔 끼운다(fetch + history). 실패하면 일반 이동.
- 고른 날 상세는 작업 카드(공종 색 띠·시간·공종·업체·버전)이고, 누르면 상세 모달(변경 제안·다른 날에도·계획 수정·삭제)이 열린다.
- 오늘을 고르면 상세 위에 ‘오늘 먼저 챙길 것’과 응원 한 줄을 둔다. 순서는 진행 중 → 곧 시작(2건) → 업체 미지정 규칙이며 AI 추천이 아니다(제품에 LLM 호출 없음, AGENTS 설계 원칙). 응원 문구는 날짜로 고르므로 같은 날은 같은 문구다.
- 홈: 머리에 진행 중·예정·끝남 숫자, 오늘 작업은 진행 막대가 있는 카드(계획 시간 기준, 실제 진척 아님), 내일 준비는 제목 줄+버튼, 예보 발표 정보는 데이터 상태로.
- 화면의 설명 문장은 빼고 **공온 가이드(/guide)**로 모은다. 이름을 누르면 내 정보(/me)·공온 가이드·로그아웃 메뉴. 화면 문구는 짧고 재치 있게(brand.md ‘공온 말투’). D-063의 ‘공온이 주어인 머리 설명’은 이 결정으로 대체한다.

## D-065 공온 점검(날씨는 일부)·홈 오늘/내일/이번 주·일요일 시작 (C04-8, 2026-10-16 개발자 피드백)

- 공온의 중심은 공정 관리이고 날씨는 그 일부다(개발자). 홈은 작업마다 **공온 점검** 다섯 항목을 본다: 날씨(내일만, 공온 판정이 ‘진행’이 아니거나 판정 전)·실행 업체 미지정·작업 위치 없음·같은 현장·날·위치에서 시간이 겹침(끝=시작은 겹침 아님)·확정 전 변경 제안. 모두 등록 자료로 하는 규칙이며 새 기준 수치를 만들지 않는다(총정리 §1.3, AGENTS).
- 홈은 위에서부터 **오늘**(시간 순 일정 + ‘먼저 챙길 것’: 진행 중 → 곧 시작 2건 → 걸린 작업과 항목), **내일**(첫 작업·준비 n/전체와 항목별 수·날씨 단계별 수 세 줄 브리핑), **이번 주 공온지수**(내일부터 7일 고리, 현장이 여럿이면 그날 가장 낮은 점수와 그 현장). 현장별 날씨 자세히는 접어 둔다. 큰 머리 카드는 없앴다.
- ‘공온 점검’ 큰 버튼 대신 날짜 옆 작은 ‘확인 시각’ 버튼, 휴대폰은 맨 위에서 당겨 놓으면 같은 실행(run-all)을 한다. 조정자에게만 보인다.
- 달력(작업 일정·날짜 고르기·작업 추가)은 일요일부터 시작한다. 주 메뉴는 가운데 정렬. 작업 추가 모달의 시간 바로가기 칩은 없앴다(최근 시간 조회도 삭제).
- 움직임: 홈 영역·목록이 차례로 떠오르고, 모달·메뉴·고르기 판·접는 상자가 부드럽게 열린다. 운영체제의 ‘동작 줄이기’ 설정이면 끈다.
- 시연 자료: `scripts/seed_demo.py`가 [가상] 원청 1곳과 골조·철골·펌프카·레미콘·크레인·방수·전기·가설 협력업체·감리와 일주일 작업을 만든다(점검이 보이게 미지정·겹침을 섞음). 실제 회사가 아니다(D-056).

## D-066 주 사용자와 참여 업체·담당자 명부 (C04-9 기획, 2026-10-16 개발자 승인)

- **주 사용자는 원청 현장의 공사·공무 담당자**다(총정리 §2.1 "일상 사용자·도입 후원자"). 작업 등록·변경 확정·조치 배정을 한다. 보조 사용자: 원청 안전·품질(검증), 소장(현황), 협력업체 현장대리인·반장(맡은 조치 응답·완료 보고, 휴대폰), 감리·CM(열람). 작업자·기사는 D-067.
- 지금 구조의 문제: 업체는 사람이 가입해 참여자로 추가될 때만 생기고(업체 단독 등록 없음), 업체를 뺄 수 없으며(멤버십 회수만), 직책이 없고(권한 3종뿐), 가입 때 회사를 새로 만들어 같은 회사가 여러 행이 된다(시연 자료도 강제로 합쳤다).
- 결정: 현장의 **참여 업체를 사람 없이 원청 조정자가 직접 등록**한다(회사 이름·구분·맡은 공종·참여 기간). 구분은 `협력업체 / 자재 공급 / 장비 임대 / 감리·CM` 네 가지로 시작한다. 업체가 빠지면 지우지 않고 **참여 종료**(종료일·처리자 기록)로 두어 실행 업체·조치 담당 선택에서만 빠지고 지난 작업·기록에는 남는다. 재개 가능.
- 업체마다 **담당자 명부**(계정 없이): 이름·직책·연락처·메모. 직책은 자유 입력 + 추천어(현장대리인·반장·공무·안전관리자·품질관리자·기사·감리원). 직책은 표시·연락용이고 **권한(조정자·담당자·열람자)과 분리**한다.
- 명부의 사람이 가입하면 조정자가 계정을 연결한다(같은 업체 소속만). 연결된 사람만 로그인해 조치에 응답한다. 연결 안 된 사람의 응답은 조정자의 전화 확인 기록(C06 `phone_record`·대리 기록)으로 남긴다.
- 회사 중복: 참여자로 추가할 때 이미 같은 현장에 같은 이름의 업체가 있으면 그 업체에 붙일지 묻는다(자동 병합 금지 — 실제 사업자 확인이 없으므로). 사업자번호는 선택 입력이며 검증하지 않는다.
- 연락처는 개인정보다. 같은 현장 참여자에게만 보이고, 열람자(감리)에게는 이름·직책만 보인다. 실제 운영 전 보관 기간·동의는 확인 항목(C08 전)으로 둔다.

## D-067 작업자(말단 노동자) 보기: 별도 서비스가 아니라 같은 서비스의 게시 화면 (C11 기획, 2026-10-16 개발자 승인)

## D-069 중기 참고 날도 공온지수 참고 점수 (C04-11, 2026-10-16 개발자 요청, D-050·D-052 범위 변경)
- 개발자: 7일 공온지수가 6~7일 뒤에 비어 있다. 있는 자료로 빨리 채운다. D-050은 중기 참고 날에 점수를 내지 않았다.

## D-071 현장 대화방(현장 단위 메신저)을 범위에 넣는다, C07 다음 C12 (2026-10-16 개발자 결정, D-070 R7 해소)

- 개발자: 슬랙·디스코드처럼 업무 대화를 사생활 메신저(카카오톡)와 나눌 곳이 필요하다. 링커리어·사람인의 지원자 방처럼 **맥락 단위로 열리는 방**이 낫다.
- 검토: 저장소에는 메신저 구현이 없었다(D-070). 건설 현장은 회사 10곳 이상이 섞이고 공사가 끝나면 흩어지므로, 회사 단위 범용 메신저(슬랙형)보다 **현장마다 자동으로 생기고 그 현장 참여자만 들어오는 방**으로 시작한다. 일반 채팅 앱과 경쟁하지 않고, 대화가 업무로 이어지는 점을 공온의 차이로 둔다.
- 결정(C12 범위): ① 현장 대화방 — 현장당 하나, 활성 멤버십이 있는 사람만 읽기·쓰기(권한은 teams 서비스, 비참여 404). 게시(board) 역할은 제외. ② 메시지에서 사람이 **변경 제안·조치 만들기**를 고르면 원문 메시지를 연결해 저장한다(자동 해석·자동 확정 없음). ③ 대화 안 변경·조치 카드는 현재 버전·상태를 그때그때 읽어 보여 주고, 메시지 본문의 일정이 현재 확정안처럼 보이지 않게 한다. ④ 읽음·"네" 답장은 수행·검증으로 바뀌지 않는다(계약 §5 상태 전이 그대로). ⑤ 메시지 수정·삭제가 조치 기록을 바꾸지 않는다. 공사 종료(현장 삭제) 뒤에도 기록은 남는다.
- 순서: C06 → C07 → **C12 현장 대화방** → C11. 조치(C06)가 있어야 "조치로 만들기"가 의미가 있다. 첫 구현은 짧은 주기로 새 메시지를 불러오는 방식(실시간 연결·푸시 알림은 필요가 확인될 때)으로 한다.
- 범위 밖 유지: 회사 전체 채널·1:1 개인 대화·파일 대량 보관·외부 메신저 연동. 필요가 확인되면 따로 정한다.
- product §6의 '일반 채팅(사내 메신저)' 제외 문구를 이 결정으로 바꿨다.

## D-073 휴대폰 번호로 가입·현장 초대, 문자 인증은 뒤로 (C04-13, 2026-10-16 개발자 요청)

- 기존 사용자의 번호는 지어내지 않고 비워 둔다. 시연 계정만 가상 번호 010-0000-0001~를 쓴다(실제 번호 아님).
- 개인정보: 번호는 찾기에만 쓰고 참여자 목록에 보이지 않는다. 보관 기간·동의는 D-066의 확인 항목과 함께 실제 운영 전에 정한다.

## D-074 후속 조치 구현 세부(C06, 2026-10-17, 개발자 승인 범위 C06 안)

- 후보는 `action_items.status = candidate`로 저장하고 확정 트랜잭션에서 `requested`로 바꾼다. 확정한 조치는 내용을 고치지 않고 이유와 함께 제외만 한다(지운 흔적이 남지 않게).
- 담당은 계정(`assignee_user_id`) 또는 계정 없는 명부의 사람(`assignee_contact_id`, D-066). 명부의 사람은 로그인하지 않으므로 조정자가 전화로 확인해 대신 기록한다(연락 상대·시각 필수, 사건에 `on_behalf`). 나중에 그 사람이 계정과 연결되면 본인이 직접 응답한다.
- 검증자는 조정자·담당자 역할만, 담당자와 같을 수 없고 보고자는 같은 조치를 검증하지 못한다(A3).
- 필수 조치 없이 확정하려면 이유를 남긴다. 변경 건 종료는 현재 확정 버전의 필수 조치가 모두 검증 완료·제외, 막힘 0건, 진행 중 제안 0건일 때만(조정자). 종료한 건에는 재변경을 제안하지 못한다.
- 처리 시각·연락 시각은 지금보다 늦을 수 없다(같음은 허용). 기한 뒤 처리는 '기한 뒤 처리'로 숨기지 않고 보인다.
- 열람(`viewed`) 사건·발송 대기·대체 조치 연결·보완 후보는 C07에서 더한다.

## D-075 재변경 때 조치 이어받기는 '후보 제시'로 (C07 일부, 2026-10-17)

- 재변경을 제안하면 지금 확정 버전의 조치를 새 버전 후보로 복사해 둔다. 미수행(요청·수행 중·막힘)은 같은 내용, 이미 완료 보고·검증한 일은 '바뀐 일정에 맞게 다시 확인' 선택 후보로만 제시한다. 사람이 고치거나 빼고 확정한다(자동 원복·자동 확정 없음, 계약 §6).
- 지난 기한은 그대로 쓰지 않고 '재변경으로 기한을 다시 정해야 함'으로 둔다. 확정하면 이전 조치는 대체됨이 되고 replaced_by_id로 새 조치를 가리킨다.
- 열람(viewed)은 수행자(본인·위임받은 사람)가 변경 건을 처음 연 시각만 남긴다. 검증자·조정자의 대리 기록 대상은 세지 않는다. 열람은 수락이 아니다(brand §3).
- 발송 대기·실제 알림은 아직 없다. 알림톡은 D-015 조건(발신 프로필·템플릿 승인·비용) 충족 뒤.

## D-076 작업에는 늘 실행 업체, 원청만 있는 현장은 작업 추가 막음 (2026-10-17 개발자 요청)

- 홈은 현장이 둘 이상이면 위에 현장 칸(전체·현장별 오늘 작업 수)을 두고, 고르면 그 현장만 보인다(휴대폰은 좌우로 밀어 넘김). 시연용 더미 자료에는 '[가상]' 표시를 붙이지 않는다(개발자 요청). 테스트 자료는 여전히 실제 회사가 아님을 문서에 적는다.

## D-078 홈 내일 요약·공온지수 표시 (2026-10-17 개발자 요청, D-052·D-069 표시 변경)

- 내일 요약은 칸 다섯: 전체 작업·진행·확인 필요·중지 검토(그 판정의 작업 수, 0건은 흰 바탕)·공온지수 원. 모두 눌러 공온 판정으로 간다. 작업 줄의 판정 칸은 그 작업의 판정을 보이고, 다른 확인할 것(업체·겹침·변경 중)은 '!'로만 표시한다.
- 이번 주 공온지수는 원 디자인을 유지한다. 현장이 여럿이면 점수가 있는 현장의 **평균**과 '현장 n곳'을 보인다(이전: 가장 낮은 현장).
- 중기예보로 계산한 먼 날 점수는 '중기 참고' 글을 붙이지 않고 옅은 점선 원과 풀이(마우스 올림·화면 낭독)로 구분한다. 계산·저장 규칙(D-069)은 그대로다. 점수가 없는 날은 '예보 전'·'점수 없음'.
- 홈의 현장별 날씨 표는 빼고 공온 판정 전체 화면에서 본다. 오늘 '먼저 챙길 것'은 '우선순위'로 이름을 바꿔 제목 오른쪽에 둔다.


## D-079 KCS 원문은 국가건설기준센터 OpenAPI로 받고, 개발용 자료실을 둔다 (2026-10-17 개발자 요청)

- KCS(국가건설기준) 원문은 국가건설기준센터 OpenAPI(`kcsc.re.kr/OpenApi/CodeViewer`, 키 `KCSC_API_KEY`)로 받는다. 웹사이트 내부 다운로드 주소로도 HWP가 받아지지만 공개 API가 아니라 바뀌면 깨지므로 쓰지 않는다. `scripts/fetch_kcs.py`가 날씨 조건(기온·강우·습도·바람·동결 등)이 들어간 문단만 조항 번호와 함께 `rules/sources/kcs_weather.json`에 발췌한다(원본 전체는 넣지 않음, D-033).
- 받은 원문(2026-10-17): KCS 14 20 40 한중 콘크리트(2024), KCS 41 47 00 도장공사(2023), KCS 41 40 01 방수공사일반·41 40 06 도막방수공사(2021), KCS 44 50 10 아스팔트 콘크리트 포장공사(2023). **기준표(rules/*.yaml)는 아직 만들지 않았다.** 발췌는 후보이며, 기준표로 옮길 때 조건·예보 비교 가능성·이상/초과를 사람이 고르고 인용 테스트를 붙인다.
- 이동식 크레인·고소작업대는 장비 풍속 제한이 순간풍속이라 예보만으로는 판정이 어렵다(D-032와 같음). 현장 풍속 입력이 생기기 전에는 기준표를 만들지 않는다.
- 바닥글 '자료실(개발용)' → `/sources`(로그인 필요): API로 받는 자료·공종별 기준 상태·받아 둔 발췌·미연결 자료를 기준표·발췌 파일·설정에서 그대로 읽어 보인다. 개발 중 확인용이며 **출시 전에 화면·바닥글 링크·`app/features/help/service.py`를 함께 뺀다.**

## D-080 모든 공종 기준을 원문 대조로 확정, 예보 경로 자동 전환 (2026-10-17 개발자 요청)

- 화면의 6개 공종 + 폭염(공통) 모두 `source_verified: true`. 인용·값·단위·이상/초과/이하/미만은 `tests/engine/judgment/test_rule_sources.py`가 발췌와 대조한다(법령·KCS·공식 PDF 모두). 기준표는 발췌 파일을 여럿 가질 수 있다(`source_snapshot` 목록).
- 판정 단계 원칙: 원문이 **금지**("…해서는 안 된다", "시공하지 않아야", 법령의 작업 중지)면 `중지 검토`, **시공 방법·협의**("한중 콘크리트로 시공", "담당원과 협의")나 수치 없는 위험 우려면 `확인 필요`.
  - 콘크리트: 한중 KCS 14 20 40:2024 1.1(2) 추가 — 일평균기온 4 ℃ 이하, 타설 완료 후 24시간 최저기온 0 ℃ 이하 → 확인 필요. 새 요소 `min_temperature_next_24h_c`(계약 v1.3).
  - 도장·방수: KCS 41 47 00:2023 3.2.17(기온 5 ℃ 미만·상대습도 85% 초과·눈·비 → 담당원 승인 전 도장 금지) → 중지 검토. 방수(KCS 41 40 01 3.5)의 협의 절차는 조치 문구에 적는다.
  - 아스팔트 포장: KCS 44 50 10:2023 3.4.7(비·기온 5 ℃ 이하 → 시공 금지) → 중지 검토, 눈은 표면 동결·습윤 확인 → 확인 필요.
  - 이동식 크레인·고소작업대: 법령·KCS에 풍속 수치가 없다(타워크레인만 순간풍속, 제37조②). 산업안전보건기준에 관한 규칙 제37조①(비·눈·바람으로 위험 우려 시 작업 중지)과 기상법 시행령 별표 1 강풍주의보 기준(육상 풍속 14m/s 이상, 평균풍속이라 예보와 같은 양)을 써서 14m/s 이상 → 중지 검토, 비·눈 → 확인 필요. 장비 허용풍속(설명서)·순간풍속은 예보에 없어 판정하지 않는다(현장 풍속계·AWS 관측 연결 시 보완).
- 예보로 판정하지 못하는 것(자료실에 표시): 안개(도장·아스팔트), 바탕·노면 상태와 이슬점, 순간풍속, 콘크리트 온도. 해외 규격(EN 280 12.5m/s 등)·연구 보고서 수치는 국내 공식 기준이 아니라 쓰지 않는다.
- 단기예보: API허브 키가 있으면 먼저 쓰고 실패(예: 활용신청 전 403)하면 공공데이터포털 키로 다시 받는다. 2026-10-17 API허브 키로 단기예보 403이 나 모든 판정이 '판정 불가'가 됐던 문제를 막는다. 둘 다 실패하면 두 원인을 함께 남긴다.
- 저장소: GitHub 비공개 전환(개발자 요청), 이 저장소의 커밋 이메일은 GitHub noreply 주소. `.env` 값이 추적 파일에 들어가면 `tests/test_no_secrets.py`가 실패한다. 이력 검사 결과 키·DB 비밀번호가 커밋된 적은 없다. 도구 캐시는 `.cache/`로 모은다.

## D-081 판정 강도: 작업이 어려울 게 분명하면 중지 검토로 거른다 (2026-10-17 개발자 결정)

- 개발자: "확인 필요가 너무 많으면 사용자가 앱을 안 쓰고 스스로 판단한다. 기준상 안 될 것 같으면 중지 검토, 정말 애매한 것만 확인 필요."
- 원칙(D-080 보완): 예보로 직접 비교한 값이 원문 기준의 **금지·중지 수준**이면 중지 검토. 확인 필요는 ① 범주 예보가 기준에 걸칠 때(예: '1mm 미만') ② 시공 방법만 바꾸면 되는 기준(서중·한중 콘크리트) ③ 법이 중지 대신 조치를 요구할 때(폭염) ④ 추정값(D-053)에만 쓴다. 비교할 수 없는 것은 여전히 중지 검토로 올리지 않는다.
- 이동식 크레인·고소작업대: 이 공종의 법정 수치가 없어 같은 고소·양중 성격인 철골 작업의 중지 기준(안전보건규칙 제383조: 풍속 10m/s·강우 1mm/h·강설 1cm/h 이상)을 **준용**해 중지 검토. 강풍주의보 14m/s도 중지 검토. 그보다 약한 비·눈만 제37조①로 확인 필요. 화면 출처에 '제383조 준용'으로 밝힌다.
- 콘크리트: 비가 오면(가이드라인 '강우 시 타설 원칙 금지') 중지 검토. 아스팔트: 눈이 와도 중지 검토(포설면이 젖거나 얼면 시공 안 함).
- 기준 버전에 `D-081`을 붙여 같은 예보라도 새 기준으로 다시 판정한다. 이전 판정 기록은 그대로 둔다.

## D-082 달력: 공휴일·주말 색·전체 달력 범위, '판정' 표시 제거 (2026-10-17 개발자 요청)

- 공휴일은 공공데이터포털 '한국천문연구원 특일 정보'(getRestDeInfo, 같은 `KMA_SERVICE_KEY`, 활용신청 승인 확인)로 해마다 한 번 받아 프로세스에 기억한다(성공 하루, 실패 한 시간). DB에 저장하지 않고 판정에도 쓰지 않는다. 받지 못하면 공휴일 없이 달력이 그대로 보인다. 대체·임시공휴일이 응답에 들어온다.
- 일요일·공휴일 날짜는 빨강, 토요일은 파랑. 공휴일 이름은 날짜 아래에 한 줄(넘치면 말줄임). 칸 높이를 키웠다(데스크톱 128px, 휴대폰 76px).
- 달력의 '판정' 표시(내일 칸 강조)는 뺀다. 판정은 홈·공온 판정에서 본다.
- 전체 달력(현장 둘 이상)은 2020년 1월~2100년 12월을 넘겨 볼 수 있다. 연도 고르기는 3행 3열(9년씩) ←→로 넘긴다. 달 고르기는 보고 있는 해 앞뒤만 페이지에 넣고 다른 해는 스크립트가 만든다(링크 수천 개로 페이지가 무거워지지 않게).
- 홈 7일 공온지수 날 패널의 공종 줄은 그 공종에서 가장 높은 단계 판정의 상세로 간다(판정이 없으면 작업 일정 그날).
